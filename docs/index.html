tickforge

A small C++20 research engine for tick data: a memory-mapped columnar store, arena memory, a lock-free pipeline, an event-driven backtest, parallel parameter sweeps, zero-copy Python bindings, and an optional CUDA kernel.

github.com/henryzhangpku/tickforge · MIT · Henry Zhang

Learning project. All data is synthetic and generated from a seed; the strategy is a deliberately simple toy whose profit on that data is a property of how the data was generated. Nothing here is investment advice.

Design notes

Columnar file + mmap

Ticks are stored as structure-of-arrays: timestamps, prices, sizes and sides each in their own contiguous column, each starting on a 64-byte boundary. A study that reads only prices touches only price pages, and a scan streams through memory the way hardware prefetchers like. Opening a file is a single mmap; columns come back as std::span<const T> into the mapping, so there is no parse step and no copy, and the OS page cache is shared between processes reading the same file. MADV_SEQUENTIAL asks for aggressive read-ahead. The cast from mapped bytes to typed spans is the case C++23's std::start_lifetime_as was added for; for trivially-copyable arithmetic types every major compiler already treats it as intended.

Memory: arenas and no allocation on the hot path

Each backtest gets a std::pmr::monotonic_buffer_resource over a 64-byte-aligned block sized up front from its parameters. Rolling-window buffers are std::pmr::vectors carved from it; allocation is a pointer bump and the whole arena is released at once. A separate test binary replaces global operator new with a counting version and asserts that feeding 200,000 ticks through a constructed backtester performs zero allocations; the arena's upstream is null_memory_resource(), so outgrowing the scratch would throw instead of silently calling malloc.

The SPSC ring

One producer, one consumer, power-of-two capacity, no locks and no CAS. The producer writes a slot then publishes it with a release store of tail; the consumer's acquire load of tail makes that slot visible. The mirror pair on head stops the producer overwriting a slot still being read. Head and tail sit on separate cache lines, and each side caches the other's index so the common case touches only its own line. The first version popped one item per release store and ran at a third of direct-replay speed, because every pop bounced a cache line between cores; consuming everything available and freeing it with one store brought the pipeline level with direct replay. ThreadSanitizer runs the concurrent tests in CI.

CRTP on the hot path, virtual for plugins

Features (FeatureBase<Derived>) and strategies (StrategyBase<Derived>) use CRTP: the call is resolved at compile time, inlined into the loop, and the compiler can keep state in registers and fuse the three feature updates. The same strategy is also available behind IStrategy, created by name from a registry in its own translation unit (so the compiler cannot devirtualise it), which is how you would add strategies without recompiling the engine or load them from a shared library.

The measured trade-off is more nuanced than "virtual is slow". Three small virtual feature updates per tick cost a clear 20–50% across runs, because each blocks inlining of a body that is only a few instructions long. One virtual strategy call per tick is within run-to-run noise (about ±5%), because the per-tick work is dominated by a log and the feature updates; an indirect branch that always goes to the same target is predicted almost perfectly. Rule of thumb: keep tiny, high-frequency operations static; put the plugin boundary around coarse units of work.

Parallel sweeps and determinism

A sweep is the cartesian product of a parameter grid, one full backtest per point, submitted to a fixed thread pool that returns std::futures. Every backtest is single-threaded over immutable data and writes only to its own result slot, so results are bit-identical for any thread count; a test compares 1, 2, 3, 4 and 8 threads, and the Python example asserts the same. The pool uses one mutex-protected queue rather than work stealing: tasks are whole backtests (tens of milliseconds), so the queue is touched a few dozen times per sweep and contention is unmeasurable. Work stealing earns its complexity when tasks are microseconds long or spawn children.

Python

The pybind11 module exposes generate, TickStore, sweep, backtest and rolling_features. TickStore.price is a read-only NumPy array whose data pointer is the mmap itself (its base object keeps the mapping alive). Sweep results are built in C++ vectors and handed to NumPy through a capsule that owns them, so nothing is copied on the way out. The GIL is released while C++ runs.

import tickforge
tickforge.generate("ticks.tf", n_ticks=2_000_000, seed=42)
store = tickforge.TickStore("ticks.tf")
res = tickforge.sweep(store, windows=[200, 500, 1000], entry_z=[0.5, 1.0, 1.5], exit_z=[0.0, 0.25])
res["sharpe"].argmax(), res["pnl"].dtype   # NumPy arrays, one row per grid point

GPU: the CUDA mental model

rolling_features_batch computes a rolling mean and EWMA volatility for many symbols at once. Data is time-major (prices[t * n_symbols + s]) and each GPU thread owns one symbol, walking forward in time. At every step the 32 threads of a warp read 32 adjacent doubles, so the load coalesces into a few wide memory transactions, the single biggest factor in GPU bandwidth. Running sums live in registers; the value leaving the window is re-read from global memory, usually from L2. Shared memory is not needed because no data is reused across threads. The kernel is bandwidth-bound, so a GPU wins only with thousands of symbols resident on the device; for small batches the PCIe copy dominates. The CUDA path is behind -DTICKFORGE_CUDA=ON; CI builds and tests the CPU fallback, which uses the same layout with symbols in the inner loop.

Production

  • CMake presets for release, debug, ASan+UBSan, TSan, Python and CUDA builds.
  • GitHub Actions: gcc and clang builds with C++, Python and CLI tests; ASan/UBSan and TSan jobs; clang-tidy with warnings as errors; Release benchmarks (whose output feeds this page); Docker image build and run.
  • A two-stage Dockerfile that runs the test suite during the build and ships a slim runtime image.
  • File format with magic, version, explicit offsets and bounds checks on open; errors surface as exceptions with the path and errno.

Limitations

  • Synthetic data only, single instrument per file, trades only (no quotes or order book).
  • The fill model is simple: market orders fill at the next tick's price plus fixed slippage, with no queue position, partial fills or market impact.
  • Sharpe is per 1,000-tick bucket and not annualised.
  • The CUDA kernel is written but not exercised in CI (no GPU runners); its numerical agreement with the CPU path is expected to within a few ULP of log.
  • Little-endian, POSIX only.
